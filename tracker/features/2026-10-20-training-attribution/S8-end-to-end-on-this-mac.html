S8 · Run the chain end to end on this Mac

In plain words

The earlier stories were each tested alone, often with stand-ins. This story runs the stages together the way the server will: attribute for two seeds, ensemble, five selects, score and analyze, all through the real stage.py tool on a throwaway copy of the record store. The inputs are synthetic (features, rollouts and returns made up over a real corrupted-dataset subset of 14 episodes), because real ones need the GPU server.

Running it end to end found three real defects (below). It also tests six refusals: features from the wrong checkpoint, the wrong episode list, the wrong dataset copy, or the wrong evaluation; a score table from another subset; and an ensemble of runs trained on different subsets. Each is refused with nothing written.

A second, real-model run (the smoke run) used a 2-step toy training of SmolVLA, the open-source robot model this project trains, and ran six stages on Apple's GPU (MPS). It finished with no failed stage. It is not attribution-grade: it had only 2 rollouts and no successes, so the agreement between metrics is undefined. It proves the machinery runs on a real model, not that the scores mean anything.

Terms (MPS, smoke run, trace, scratch store, key contract) are in the report glossary.

Why

The plan's compliance matrix noted that the key contract (scores belong to exact episode versions) was only unit-tested with monkeypatching, and the brief required separating what can be re-verified on this Mac from what needs the server. PoC §2.1 item 1 asks that everything be traceable.

"Every eval rollout should be tied back to that checkpoint." — §2.1 item 1, p. 3

Example

Three defects that only the end-to-end run revealed (found and fixed in S8; all invisible to the unit tests that stub the lookup):

  1. A lineage trace from a select run dead-ended at the score table: the select recorded a fingerprint of the table's columns, while the ensemble run recorded the file's fingerprint, so no link connected them. select_run now also records the score run's output fingerprint.
  2. A select that was refused (stale score table, or a k that would empty a task) still left a FAILED run in the record, because the check ran inside the run. The checks now run before the run is created.
  3. Check 3.6c of S3 expected one kind of error for an unknown column; after fix 2 a different check fires first. The check now asserts a refusal with no run created, whichever check fires.

The smoke run's timings (artifacts/s8_local_smoke.json, final code): evaluation 85.1 s, returns 1.8 s, train features 333.8 s (40 samples; dominated by opening the dataset), rollout features 31.3 s, attribute 6.3 s, select 2.6 s; total 461 s. The select child had 38 episodes (40 minus 2) and declared the functional F(30) = P(T <= 30 s).

Divergences and limitations

  • The integration inputs are synthetic; it proves the plumbing and the refusals, not any attribution result.
  • The smoke run is not attribution-grade: a 2-step toy checkpoint, 2 rollouts (0 successes), 1 training sample per episode. 15 metric pairs each have n = 2 episodes with rollouts, so Kendall's τ is undefined (NaN) and nothing about agreement can be read from it. Its per-task columns are NaN for tasks without rollouts, so its select used the global column.
  • The trace has three intended dead ends (features, subset, score_table): inputs with no producing run in the fixture.
  • The score stage needs a score table keyed exactly to the named subset (the full v3/candidate on the server; the integration uses a small named subset).
  • Not verified here: anything needing the GPU server (see the report's "Out of scope" list).
