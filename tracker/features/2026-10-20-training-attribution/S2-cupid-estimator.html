S2 · Make the estimator CUPID's, and record every difference

The default quantity whose gradient we take is now CUPID's own (the square of the model's output), parity with CUPID's released code is checked to 2.8e-14, and nine remaining differences are named with their source.

In plain words

Influence is a number for each training recording that says how much it pushed some later outcome up or down. CUPID is the research method (a paper, plus MIT-licensed code) that computes this for robot policies, and the project's spec calls it the "best starting point to fork". To compute influence you take a gradient (the direction in which the model's numbers would have to change) of some chosen quantity, called the output function, for each training sample and for each rollout.

The ported code took the gradient of the training loss. CUPID's paper says that choice "works poorly in practice" and uses the square of the model's output instead. We switched the default to CUPID's choice, tested our arithmetic against CUPID's own two functions (they agree to 2.8e-14), and wrote down every place we still differ.

This changes what the next server run computes. Feature files made with the old default are not comparable with new ones. On 13 real samples the two choices point in noticeably different directions (cosine 0.402 at worst, 0.870 median), so the choice is not cosmetic. What we cannot say yet is whether it changes which recordings come out as harmful; that needs real runs.

Terms (CUPID, influence, gradient, output function, return, centred, Kendall's τ, Gauss-Newton, projection) are in the report glossary.

Why

PoC §4.3 says the estimator is CUPID's; §6 says to fork it. The plan found that the port computed CUPID's loss form, which CUPID's paper rejects, and that several other differences (centred returns, fewer random draws, a different projection) were either unrecorded or recorded with a wrong formula.

"The estimator is CUPID's; the way it is applied is not." — §4.3, p. 10

Example

Take one real sample from episodes 31 and 41 of the clean reference set. Its objective under the square function was 1.697 and under the loss function 2.371 (index 0 of s2_cpu_smoke_mps.json), and the cosine between the two projected gradient vectors was 0.813. Sample 7 of the 13 was the extreme case: cosine 0.402. In words: for most samples the two choices agree broadly, but for some they point in clearly different directions, so the output function changes what the influence scores mean.

Divergences and limitations

The nine differences from CUPID that remain (in DIVERGENCES) are listed in plain terms in the report's CUPID-fidelity table. Three notes specific to this story:

  • The default changed. Square on both sides is CUPID's; the owner asked this to be flagged because it changes the next server run's output. --preset branch reproduces the old loss/loss features; --preset athena is ATHENA's mixed form.
  • Centred returns are still the default for binary columns. That is the planner's assumption (inferred), not an owner-approved choice, and it differs from CUPID's ±1. This is an open owner decision in the report.
  • The square objective averages over valid steps times action dimensions, following SmolVLA's own loss reduction. CUPID's code averages over all entries including padded ones. They are equal when nothing is padded (documented in square_objective).
  • The 2-step checkpoint smoke proves the machinery, not the quality of any scores.
