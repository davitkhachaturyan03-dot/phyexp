← Training and attribution: checking the ported influence code

S1 · Every method input goes through the blind loader

Training, feature extraction, attribution and selection can no longer open a dataset version that is fenced, built from the answer key, or altered on disk.

ACs 6/6 Depends on — Glossary report.html#glossary

In plain words

We are building a method that hunts for harmful training recordings. To judge it fairly, it must not be able to cheat by reading the answer key, the table that says which recordings we deliberately damaged. An earlier feature built one safe door for this, a function called open_for_method. It refuses any dataset version that is marked off-limits (a fenced version), any subset derived from the answer key, and any copy whose bytes no longer match their recorded fingerprint.

The code ported from the owner's cluster did not use that door everywhere. Attribution used a weaker check, and the training and feature-extraction commands used no check at all. This story sends all four entry points through the door.

Result: 20 of 20 unsafe combinations (four entry points times five unsafe inputs) are refused, nothing is written when they are refused, and a clean version still opens. This matters because a method that could peek would make every later recovery number meaningless.

Terms used here (blind, fenced, v1/v2/v3, content hash, MLflow, LineageError) are defined in the report glossary.

Why

PoC §2.1 item 4 asks us to plant known damage and check whether a method finds exactly that damage. That only works if the method cannot see which recordings were damaged. The owner's earlier decision 3 made open_for_method the single method-facing loader; the ground-truth feature recorded that two stages bypassed it (a known issue).

"Deliberately corrupt known subsets of training data ... Then check whether your attribution method flags exactly those." — §2.1 item 4, p. 3

Divergences and limitations

  • The plan's demo named select as a fourth entry point but its deliverables did not; cmd_select now opens its parent through method_view too. A small addition, not a scope expansion.
  • Only the order of checks changed inside open_for_method: a version that is both fenced and tampered now reports the fence first.
  • train_run itself is untouched on purpose: the ground-truth feature's oracle arms legitimately train on answer-key-derived subsets, so the gate sits at the method chain's entry, not inside the trainer.
  • The plan's premise that opening a version takes about 20 s did not hold on this Mac (2.3 s for 960 episodes with a warm cache); either is acceptable per job.
