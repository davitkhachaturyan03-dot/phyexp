S2 · Reading Round A back from the lineage store

Three loaders find the Round A chain of a score run, read its verdicts with a checksum test, and recover the full list of removed episodes.

ACs 4/4 Depends on S1 Data demo is SYNTHETIC; no real Round A yet

In plain words

Everything the server does is recorded as runs in a store (MLflow), each with files attached. The page needs to find the right ones: the summary of the removal tests, the individual verdicts, and which training recordings each curated arm removed. This story adds the readers. They refuse a file whose checksum no longer matches what was recorded, and they say "none recorded" (rather than crash) when the score run never had a Round A.

One detail: the store keeps the removed episodes as a shortened list. For the demo, the stored tag held only 78 of the 100 ids. The reader therefore recomputes the full list as "the parent subset minus the child subset", which is exact.

Terms are defined in the glossary of the main report.

Why

PoC §9.1 Step 4 says the output is confirmation or refutation that the attribution is causally correct, and §2.6 says what is removed must be traceable. The dashboard reads only through results.py (no hard-coded paths), like the other pages.

“Output: Confirmation, or refutation, that the attribution is causally correct.” — §9.1 Step 4, p. 19

Divergences and limitations

  • The loaders are thin adapters over find_runs and runs_with_param (MLflow's search_runs underneath). The analyzer's audit found nothing off the shelf for “the Round A chain of this score run”.
  • On the server the select runs record __same_task columns; the demo records the all-rollout column (see S3). The loaders handle both.
  • Seen only on the demo store and scratch copies; the real server summary is first read the day Round A finishes (S5 proves the shape).
