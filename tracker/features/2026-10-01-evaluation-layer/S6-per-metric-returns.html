S6 · One return per metric per rollout: the attribution-ready output

Each rollout now carries a separate return for every PoC yardstick (F(30 s), RMST, AUC vs human, HRT, censored tail), each a declared functional with its time cap τ. The mean of each return equals the metric the verification gate tests, to 7.1e-15 on real rollouts. This is what CUPID's binary success_mask becomes in this PoC, and the input to the episode × metric matrix.

Why

"Success within 30 s → binary return; RMST → negative capped time; AUC → win indicator against a sampled human time. HRT is a ratio, so it needs a first-order (linearized) approximation" — PoC §4.3, p. 10
"Define one 'return' per metric for each rollout." — PoC §9.1 Step 3, p. 19

The PoC names its headline novelty on p. 1: "per-metric and per-failure-type returns producing an episode × metric matrix" (quoted). CUPID's released code aggregates influence with a binary per-rollout success mask (plan P25, quoted source). It needs a real-valued return per metric, and that is what this story emits. Returns are defined after the rollouts exist, from primitives stored in the record (docs/dataflow.md, "Returns are defined at Step 3, not Step 2").

Divergences and limitations

  • Family W is the headline on libero_10 (plan r2, option a), not per-sub-task T. §3.5 A asks for per-sub-task T, which family O keeps with its own verdict and return. The per-rollout returns follow §9.1 Step 3 and CUPID Prop. 1, which weight whole rollouts.
  • rmst60_op_cap is pessimistic by declaration. It equals the operation KM RMST only when no operation is censored before 60 s (38.15 vs 36.99 s on libero_10:8). Family-O claims must carry the _cap label.
  • The AUC counts ties as ½ on LIBERO (model and human times share the 20 Hz grid). PhAIL's validation keeps PhAIL's ties-dropped rule. The two are not comparable across the PhAIL and LIBERO reports without saying so (plan R15). The family-W AUC identity also needs every human time under 60 s; the measured maximum is 24.75 s.
  • ret_auc_expected, the deterministic expectation of §9.1's sampled indicator, is a recorded addition (lower variance, inferred). The literal sampled return is kept as ret_auc_sampled.
  • The HRT return's form is the planner's derivation (inferred). §4.3 says only "first-order (linearized)". The attribution feature should re-derive it against CUPID §D.2. Its weights use the cells of one eval run (J = 1 here; J = 20 under the server plan).
  • Failure types. Built: success, timeout_no_progress, timeout_partial_k_of_n. Not built: missed grasp, wrong object, ignored instruction and idle. LIBERO defines no such rule (its predicates are true, false, in, on, up, printjointstate, open, close, turnon, turnoff), and the catalog's exact-zero idle rule does not transfer to policy actions. The raw signals (goal-conjunct trace, task-object positions, arm-action norm) are in every record, so rules can be added without new rollouts. Ghost events: out of scope (owner decision 6).
  • F1, refreshed here. The committed AC6.3 artifact listed the two AUC columns in round 1's order. HEAD's code writes ret_auc_expected before ret_auc_sampled (registry order). The set of columns, the shape (960, 8) and every other AC6.3 value were unchanged. On 2026-10-11 the summarizer replaced artifacts/s6_verify_returns.json with the refactorer's regenerated copy (data/scratch/refactor_baseline/changed_artifacts/). git diff shows only those two lines swapped.
  • Pending server: returns at scale (AC6.7). Every number here comes from 20 rollouts of an external checkpoint, which validates the pipeline, not a policy.
