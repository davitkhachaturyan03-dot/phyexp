S0 · Fix the answer-key leak

The table a screening or attribution method reads no longer reveals which episodes were corrupted. Three leak channels were found in v1 and closed for every future derived version. v1 itself is fenced off from method use.

ACs 7/7 met Depends on — Owner ruling A, "Fix code, fence v1"

Why

Owner request (brief, verbatim): "also fix the leak now as a separate story inside the feature." The injection test only works if the method under test cannot see the ground truth. The orchestrator measured that v1's method-facing episode table had a column, parent_content_hash, that differed from content_hash in exactly the 100 labelled episodes (measured, brief). Planning then found a second channel: the 100 corrupted episodes were episode_index 900–999, a contiguous tail (plan P2, measured). The executor found a third: they also sat in their own data files, 73–80 of 81 (measured, execution log S0).

"Then check whether your attribution method flags exactly those." — PoC §2.1 item 4, p. 3

What was built

File / functionWhat it does
vlapoc/derive.py::derive_versionWrites a derived version in one LeRobot writer pass, in the parent's episode order. An edited episode is rewritten in place instead of being appended, so episode_index and the data-file layout stay the parent's. Pre-edit hashes go to the lineage-only parents.parquet.
vlapoc/lineage.py::compare_blind, check_blind, blind_reportCompare a derived version's three method-facing tables (version table, catalog copy, LeRobot meta/episodes) with the parent's. They return every column that is not a declared data-derived column but still differs, plus a pseudo-column (row order) if rows were reordered. Any column not on the data-derived list counts as bookkeeping, so a new column cannot slip through.
vlapoc/lineage.py::parent_hashesReads the pre-edit fingerprints. Documented as LINEAGE-ONLY: methods under test must not call it.

scripts/fix_v1_leak_s0.pyIdempotent: moves v1's parent_content_hash into parents.parquet, rewrites v1's two tables with v0's 21 columns in v0's row order, and writes fence.json.

Example

v1, before and after the fix. Re-run on 2026-10-11 (summarizer_rerun_stdout.txt); the before line is s0_check_blind_v1_before.txt:

$ .venv/bin/python -m vlapoc.lineage version check-blind v1      # before (2026-10-02)
check_blind(v1) = ['(row order)', 'episode_index', 'parent_content_hash']; fenced: False

$ .venv/bin/python -m vlapoc.lineage version check-blind v1      # now
check_blind(v1) = ['episode_index']; fenced: True
$ .venv/bin/python -m vlapoc.lineage version check-blind v0
check_blind(v0) = []; fenced: False

v1's version id is the same before and after (16076b9c5cb2…), because the id hashes the sorted (episode_id, content_hash) pairs and not the row order (plan P3). The label join is unchanged: 100/100. The one channel left is positional, so v1 is fenced, and the injection feature will derive its real corrupted versions with the fixed derive_version.

Divergences and limitations

  • v1 is fenced, not re-derived (owner-approved, BLOCKING Q1, ruling A, 2026-10-02). The data+lineage S6 evidence that used v1 stays intact. check_blind(v1) still reports episode_index.
  • Nothing enforces the fence yet. assert_blind exists, but no screening or attribution method exists to call it (analysis-r1, judged acceptable). Those features must call it on their input version.
  • Cross-version channel (inferred, not built). parent_hashes(v1), v0's own table and diff_versions(v0, v1) all name the edited episodes. That is correct for lineage code, but a method under test must be confined to the derived version and its reference subset.
  • Cost. The writer pass wrote 375.9 frames/s on the scratch derivation (measured). At full scale that is about 8.9 min, against about 5 min for the old delete + merge (inferred extrapolation).
  • An unexplained 980 s stall in hash_stored_dataset during one scratch derivation. A re-run took 3.1 s, so it did not reproduce.
  • Leftover: data/lineage_scratch/ (2.3 GB, a data+lineage scratch store) still holds a stale v1 table with the leaked column. Nothing reads it. Cleanup is the owner's call (N4).
