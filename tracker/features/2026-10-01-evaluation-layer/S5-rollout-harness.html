S5 · Rollout harness, rollout record and the eval stage

The first real closed-loop rollouts in the repo. A thin adapter over LeRobot's own rollout() records, per rollout, whether and when the LIBERO goal check succeeded, per-sub-task times, a fixed initial state with both its state and fixture hashes, and the lossless trajectory that CUPID-style attribution needs. Each eval is an MLflow run tied to its checkpoint, replacing the old stand-in. Validated on 20 SmolVLA rollouts (external checkpoint).

ACs 9/10 met AC5.8 pending server Depends on S3, S4

Why

"Run many rollouts per task (e.g. 50) with fixed initial states." … "record whether and when it succeeded, using the benchmark's goal check." — PoC §9.1 Step 2, p. 18
"Every eval rollout should be tied back to that checkpoint." — PoC §2.1 item 1, p. 3

CUPID's estimator weights every state-action pair a rollout visited by that rollout's return (CUPID Prop. 1, p. 5). So the store must keep trajectories, not only outcomes. LeRobot's lerobot-eval keeps only per-episode aggregates, and its recording is lossy video (quoted, lerobot_eval.py), which is why a probe and a lossless capture were added around its unchanged rollout().

No published success rate exists for this checkpoint (model card and LeRobot docs, fetched 2026-10-04), so these numbers are compared with no reference and say nothing about the checkpoint's quality. They show only that the harness runs a real policy and records real outcomes.

Divergences and limitations

  • LeRobot's LiberoEnv cannot run a 60 s episode as shipped. LIBERO's inner horizon is 1000 steps, minus 10 settle steps; unpatched, it raised executing action in terminated episode at step 991 (measured). ProbedLiberoEnv raises the horizon.
  • LIBERO moves fixtures on re-reset (measured, inferred unintended upstream). object_property_initializers grows on every hard reset, so in 4/20 tasks one env object reset 3× with the same seed moved libero_10:8's stove by 7.2 mm. The harness builds one fresh env per rollout, and t0_model_sha256 now detects a violation, which t0_state_sha256 cannot.
  • SmolVLA outcomes depend on the batch plan (measured: init 4 succeeds at step 71 at batch 1 and never at batch 5). The policy draws flow-matching noise from torch's global RNG per batch. Per-rollout policy RNG would need LeRobot internals patched (out of scope), so the fixed batch plan (batch 50, one task per batch, eval seed 0) is the declared control, following LeRobot's paired-comparison guidance.
  • The batch-2 evidence slip, resolved. A stalled executor wrote "That stub import was a slip on my part" and left contradictory AC5.2 results. The replacement executor traced each file. The committed {arm_action_norm: 6} was a comparator artifact (numpy truncates str(ndarray), reproduced by comparing a record against itself). The heredoc ACT output, whose provenance cannot be checked, was renamed s5_ac5_2_ac5_3_act_stdout.INVALID.txt and superseded by a clean recheck. The analyzer reproduced the recheck.
  • Round-1 runs mis-tagged eval.attribution_grade=true (3392bb4d, fe507fa3, and the verify run 7080353a): read the tag as "has a train run". MLflow history is append-only, so they were not rewritten; they lack the .asserted tag, so no verdict counts them.
  • Known issues (non-blocking): N1, scratch-store tests write outputs into the real data/eval/. N2, round-1 records, including both SmolVLA runs, fail validate_record for the missing t0_model_sha256. N3, the batch-plan key omits τ, render size and device. F2, the trajectories entity id hashes a physical copy, so a bit-identical re-run gets a new id (LeRobot writes stats.json keys in a varying order).
  • Cost on this Mac: 0.29–0.4 s per env-step on MPS (the checkpoint re-plans every step), so one failed 1200-step rollout ≈ 6 min. AC5.8 is server work.
  • New dependencies and downloads: transformers 5.5.4 and num2words 0.5.14 (the lerobot[smolvla] extra); smolvla_libero 1,218,055,540 bytes; SmolVLM2's 11 non-weight files (4,866,925 bytes), not its 2.03 GB weights.
