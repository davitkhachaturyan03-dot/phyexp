S2 · Instruction edits and the blind check

The derive step can now swap an episode's language instruction, and the blindness check now treats the instruction as content, so a swap passes while a provenance leak is still caught.

ACs 7/7 Depends on S1 Code vlapoc/derive.py, vlapoc/lineage.py

In plain words

A dataset version must carry no trace of which episodes were edited that a method under test could use; that property is called blindness. This story taught the dataset-writing step to swap an episode's text instruction, and fixed the blindness check so that a swapped instruction counts as ordinary content (a method may see it, and spotting it is the method's job) while a real leak, such as changing the task name that records where an episode came from, is still caught and named. The checks give identical results however Python's random hashing is seeded. This matters because a check that wrongly flags a legitimate swap, or misses a leak, would make the whole experiment untrustworthy.

Unfamiliar term? See the glossary in the overall report. Technical detail follows below.

Why

Two blockers stood between the swapped-instruction corruption (§2.5, "annotation errors") and a derived dataset. First, derive_version refused task edits outright. Second, the blind check counted the instruction as bookkeeping, so a swap would have failed it, or worse, an instruction could have become a free side channel that tells a method which episodes were edited. The PoC's rule is that a method must be able to flag the planted episodes on its own.

Then check whether your attribution method flags exactly those. — §2.1 item 4, p. 3

The repo already hashes the instruction into every episode's content hash (vlapoc/catalog.py:127-148, read in the plan, premise P10), so counting it as content is consistent with how identity already works.

Example

The swapped episode in the 20-episode scratch version is pick_up_the_black_bowl_on_the_ramekin_an…/demo_0. Before the edit its data rows carried task index 5. After, all 137 rows carry index 7, which is the parent's index for the target instruction, and meta/episodes holds the string "pick up the black bowl on the stove and place it on the plate". The task table itself is untouched, and only this one episode's index differs from the parent's. Nothing else changed: task_name, episode_id, scene and objects stay true, as they would in a real mislabelled dataset.

What to notice: the swap itself is accepted because the instruction is content, while every attempt to hide or signal the edit through bookkeeping (provenance columns, a mismatched meta table) is caught and named.

Divergences and limitations

  • Extra rule beyond the plan. Moving tasks out of the bookkeeping set alone would have let meta/episodes.tasks drift from the catalog instruction unnoticed, so the consistency rule was added and tested (AC2.6).
  • Swaps keep true provenance (design D1). A cross-check of the instruction against task_name finds every swap (AUROC 1.000, S5 heuristic H6). Hiding provenance with opaque keys is option B of the dispute; the owner ruled it out of this feature (ruling A) and it is recorded as limitation B in the report.
  • The v1 labels have no hypothesis column (v1 is not rebuilt).
  • The scratch parent is a 20-episode miniature whose stored content hashes equal v0's for the same episode ids (20/20), so it is faithful, but it is not the full-scale run (that is S4).
