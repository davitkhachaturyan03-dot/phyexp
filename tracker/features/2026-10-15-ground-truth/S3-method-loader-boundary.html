S3 · The method-facing loader and the answer-key boundary

One door, open_for_method, that a screening or attribution method must use to read a version. It refuses fenced, tampered, answer-key-derived and diff-able versions, and a source scan proves methods never touch the labels.

ACs 6/6 Depends on S2 Code vlapoc/method_data.py (172 lines), vlapoc/groundtruth.py::load_answer_key

In plain words

A method that is being tested must not be able to peek at the answer key (the record of which episodes we damaged) or at side clues to it. This story built the one entry point, the method-facing loader (open_for_method), that a method must use to read a dataset version. It refuses versions that are fenced (marked off-limits), tampered with, built from the answer key, or that would let a method compare two versions of the same dataset (the difference would name the edited episodes). A scan of the source code finds 0 violations and catches 6 of 6 planted ones, which shows the scan can actually fail. This matters because without the gate, a method's score could come from cheating rather than from skill.

Unfamiliar term? See the glossary in the overall report. Technical detail follows below.

Why

Owner decision 3 ("Enforce now") asked for a single loader that always calls lineage.assert_blind and respects the v1 fence, so that later screening and attribution features cannot read a leaky or fenced version by accident. This closes a known issue from the evaluation feature: the v1 fence was recorded but nothing enforced it at a method's entry point. The answer key stays readable only through an explicitly ground-truth-side path, groundtruth.load_answer_key, used for scoring recovery@k.

Then check whether your attribution method flags exactly those. — §2.1 item 4, p. 3 (a method that can read the labels, or a leaky version, would not be flagging them on its own)

Example

What a method sees when it asks for each version of the real store (artifacts/s3_r3_run.txt, run in round 3):

open_for_method("v1/candidate")
  LineageError: version v1 (16076b9c5cb2) is not blind to its edits: fenced=True, offending=['episode_index']
open_for_method("v2/candidate")
  LineageError: version v2 (eaeed043455a) is fenced: superseded by v3 (002a68e4caf2); use the superseding version
open_for_method("v0/candidate")
  opened: 960 episodes, 40 reference ids; first episode demo_0 action (98, 7) image (98, 128, 128, 3)

v1 is refused because its edits were the last 100 episodes by position (an edit leaked through episode_index), and v2 because it was replaced. v3, the current ground truth, opens (its catalog never carries a label).

Divergences and limitations

  • Trainers are not covered. The loader protects methods, not trainers: vlapoc.runs.train_run and eval_run do not call open_for_method or assert_blind. That is correct for this feature's own training arms (they must train on the corrupted data), but a later method that trains policies (datamodels, CUPID) could hand a ground-truth-derived subset to train_run and not be refused, and train_run("v1/candidate", …) would run on the fenced v1. Known issue for the attribution feature (recorded in the runbook, AC6.6): route training inputs through the loader. Not fixed here.
  • Cost. Every open_for_method call hashes the whole version (about 20 s for v0). That is what the AC asks for, so a method that opens a version many times pays each time.
  • The catalog still shows provenance (task_name, episode_id, position) next to the instruction, by design D1. A swapped instruction is therefore findable by cross-check. Limitation B of ruling A.
  • Convention, not a mechanism. A ground-truth-derived subset is recognised by its op name or tag; a later feature that builds one must use oracle_drop, a name containing groundtruth, or a groundtruth tag. The scan checks imports and string literals in method code; it is not a sandbox.
  • Off the shelf: import-linter can forbid imports but not string literals (labels.parquet) or attribute names (parent_hashes), which the AC requires. The analyzer judged the roughly 30-line AST scan worth keeping and noted import-linter could replace its import half.
