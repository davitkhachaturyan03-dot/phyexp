S5 · Every stage as an MLflow run, and the trace / consumers / diff queries

Each PoC stage now records itself as an MLflow run in a local SQLite store. The run names the exact episode versions it consumed and the entities it produced, plus the git SHA. Three queries read them back: where did this run's data come from, which runs used this episode version, and what changed between two runs.

ACs 10/10 met Depends on S3, S4 Backend MLflow 3.16.1, data/lineage/mlflow.db (owner: local)

Why

"Every training run should be tied to exact dataset versions (content hashes), episode IDs, mixture weights, augmentation settings, the config, the git SHA, and the resulting checkpoints. Every eval rollout should be tied back to that checkpoint. W&B Artifacts, MLflow, or DVC handle this well. … it lets you answer "what changed between the good run and the bad run?"" — §2.1, p. 3
"The most compelling output is where screening and outcome attribution disagree" — §9.2, p. 19. Both score tables must therefore share episode-version keys.
"Remove the top-k "helpful" episodes and retrain" — §2.6, p. 5 · "Randomized subset training with regression (datamodels-style)" — §2.1 item 5, p. 4

The backend is the owner's choice (Q1, brief.md): "MLflow, local", meaning SQLite, no account and offline.

Divergences and limitations

  • Training goes through LeRobot's train(), not the lerobot-train CLI. On Python 3.14 the CLI fails while building its parser (TypeError: str | None is not callable), the bug of draccus issue #69, which is open. lerobot 0.6.1 declares only Python 3.12 and 3.13 (its METADATA classifiers); the venv is 3.14.0. The sampler, training loop, checkpointing and train_config.json are LeRobot's own. from_pretrained fails the same way, so load_checkpoint uses draccus.load plus a strict safetensors load.
  • The MLflow dataset digest is capped at 36 characters (MAX_DATASET_DIGEST_SIZE = 36). The digest is a 32-hex prefix (128 bits); every query re-checks the full id from the tag.
  • Normalization-stats leak (open decision for the training feature). LeRobot normalizes with the whole version's meta/stats.json, which covers all 1000 episodes: the 40 references, the 100 corrupted and any dropped episodes. A checkpoint trained on the 40-episode reference subset saved stats equal to v0's full file (measured). Each run records stats_json.sha256, normalizer.sha256 and a normalization_stats param. Fixed-reference or per-subset stats is not decided here.
  • A refused drop_group inside select_run leaves a FAILED run. direction is validated before the run starts; column and value are not (analyzer, measured). The run is inert, because only FINISHED runs form lineage edges.
  • The select.dropped tag is truncated at 7,900 characters, which leaves an invalid-JSON prefix for large drops (about 47,400 characters at k = 480). The subset file is the record of truth.
  • Datamodels scale. Each random-subset record stores episode_ids and dropped (about 95 KB at n = 480) plus one MLflow run. At DataMIL's m = 10⁴ that is roughly 1 GB of JSON and 10⁴ runs (analyzer, inferred); a mask-matrix artifact would scale.
  • New dependencies: mlflow==3.16.1 (owner Q1) and accelerate==1.15.0, which LeRobot's train() requires (require_package("accelerate")). The repo has no dependency manifest; versions are recorded in the execution log only.
  • MLflow keeps some absolute paths in its own records (experiment artifact_location, mlflow.source.name). Our manifests hold none. Moving data/lineage to another machine needs the artifact location remapped (inferred; untested).
